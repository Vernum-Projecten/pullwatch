Once a day, and whenever you choose **Check all**, Pullwatch reads the manifests and lockfiles on the default branch of every repository you follow. It finds the runtimes, frameworks and packages, and compares them with what is current. You can turn the daily check off under Settings, General.

## Runtimes and frameworks

| File | What Pullwatch finds |
|---|---|
| `go.mod` | Go |
| `*.csproj`, `*.fsproj`, `Directory.Build.props` | .NET |
| `package.json` | Node (`engines`), Angular, React, Vue, Next.js, Nuxt |
| `composer.json` | PHP, Symfony, Laravel |
| `rust-toolchain`, `rust-toolchain.toml`, root `Cargo.toml` | Rust |
| `Package.swift` | Swift, compared with the releases on swift.org |
| `.nvmrc`, `.node-version`, `pyproject.toml`, `.python-version` | Node, Python |
| `Dockerfile*` | base images such as node, golang, python, dotnet, alpine, debian, ubuntu, nginx, postgres, redis, eclipse-temurin, rust, php and ruby |
| `.github/workflows/*.yml` | `python-version`, `node-version`, `go-version`, `dotnet-version` |

Versions are compared with [endoflife.date](https://endoflife.date) and get one of four states: **Current**, **Behind** (a newer major or minor exists; patches do not count), **EOL** or **Unknown**. Swift has no end-of-life policy, so it is never EOL.

A few rules keep the result honest:

- A requirement that is only a minimum (`engines.node`, `php` in `composer.json`, `requires-python`, `rust-version`, versions in CI) is dropped when the same language is pinned elsewhere, such as a Docker image, `.nvmrc` or `rust-toolchain`.
- For frameworks, the installed version from `package-lock.json` or `composer.lock` wins over the minimum in the manifest.
- A `go.mod` used as a local copy of a dependency (`replace ... => ./path`) is ignored.
- Custom Docker images are recognized by a known name before the first dash (`php-fpm-alpine:8.4` is PHP 8.4), and `ARG` defaults in `FROM` are filled in.

## The Dependencies section

**Dependencies** in the sidebar turns the check around: per runtime and package, the latest version, and which repositories are still on an older one. It updates with the version check (daily, **Check all** and **Check now**), and its badge in the sidebar counts the new versions you have not seen yet that you can take now or that fix a vulnerability.

<Screenshot name="dependencies" alt="The Dependencies section grouped into Can update now, Needs a manifest change and Blocked, with lodash blocked in one place by express and body-parser." />

- **Runtimes** (Go, Node, PHP, Python, .NET, Rust, Swift and Docker images) are compared within their release cycle, patches included. A repository on Go 1.27.3 sees that Go 1.27.4 is available, and one on Go 1.26.9 sees 1.26.10 once that is out. A newer cycle (Node 22 to 25) shows on the repository as behind instead. A version without a patch (`go 1.27`, `node:22`) is never behind on patches.
- **Packages** are the direct dependencies, from the root and each workspace. Development-only packages are marked as such. A package without an exact version (a range without a lockfile) is not counted. Frameworks (React, Angular, Vue, Next.js, Nuxt, Laravel, Symfony) appear once, as a package.
- The latest version comes from the package's registry: proxy.golang.org, registry.npmjs.org, repo.packagist.org, api.nuget.org, pypi.org, crates.io and rubygems.org. A package one of your followed repositories publishes itself comes from your own registry instead (see [In-house packages](#in-house-packages)). Pre-releases do not count. Other private modules and Swift packages end up under **Can't be checked**.

How Pullwatch knows a package is direct:

| File | Direct packages |
|---|---|
| `go.mod` | lines without `// indirect` |
| `package-lock.json` (v2 and v3), `pnpm-lock.yaml` | the root and the workspaces |
| `packages.lock.json` | packages marked `Direct` |
| `Gemfile.lock` | the `DEPENDENCIES` section |
| `composer.lock`, `Cargo.lock`, `poetry.lock`, `uv.lock`, `yarn.lock` | the names in `composer.json`, `Cargo.toml`, `pyproject.toml`, or the `package.json` of the root and each workspace |
| .NET `PackageReference`, `requirements*.txt` | every package, since they are direct already |

Development-only packages come from `devDependencies`, `require-dev`, dev groups, and the `group :development, :test` blocks of a `Gemfile`.

The groups tell you what an update takes: **Can update now** fits the range in your manifest, so only the lockfile changes; **Needs a manifest change** is outside that range, such as a new major version; **Blocked** means another package holds it back, and the row says which one.

A package that no repository asks for itself, and that only comes in through another package, appears under **Only transitive, with a vulnerability** when it has a known vulnerability, with the chain that pulls it in. Pullwatch looks up the latest version only for packages a repository asks for itself. For Rust, the requested ranges come from every `Cargo.toml` of a workspace, including the `[workspace.dependencies]` that members take over with `workspace = true`.

## In-house packages

A dependency that one of your followed repositories publishes to the registry of its own service (GitHub Packages, a GitLab registry or an Azure Artifacts feed), and that your repository provably gets from there, is an in-house package. npmjs.com or nuget.org do not know a private `@acme/ui`, so Pullwatch takes its latest version from your registry, which [Packages](/using/packages/) lists. The row says **In-house**, with a link to the repository that publishes it, and its tooltip says "Published by octocat/linguist: the latest version comes from your own registry." Ranges, the update groups and what blocks an update work as for any other package.

### Evidence, not the name

A name alone does not make a package yours. An organisation can publish a patched fork of a public package under the same name, such as `Newtonsoft.Json`, and a repository that uses the public package must keep its public latest version and its known vulnerabilities. So Pullwatch counts a dependency as in-house only with evidence:

- npm: a name with the owner's scope (`@acme/ui` published by `acme`; on GitLab the top-level group, on Azure DevOps also the organization).
- Go: the module path, which names its own host and owner.
- Every ecosystem: the registry the lockfile or manifest names is the account's own registry for that ecosystem. Pullwatch reads it from `resolved` in `package-lock.json` and a classic `yarn.lock`, `remote:` in `Gemfile.lock`, `dist.url` in `composer.lock`, `--index-url` or `--extra-index-url` in a `requirements` file, the source of a package in `poetry.lock` and `uv.lock`, and `source` in `Cargo.lock`. Own registries are `npm.pkg.github.com`, `nuget.pkg.github.com` and `rubygems.pkg.github.com` with the owner in the path (on GitHub Enterprise `npm.<host>` or `<host>/_registry/npm/`), `/api/v4/…/packages/…` on the GitLab server of the account, and `pkgs.dev.azure.com/<organization>/…/_packaging/…` for Azure Artifacts.

`packages.lock.json`, `pnpm-lock.yaml` and the `yarn.lock` of Yarn 2 and later name no registry per package, so a NuGet package, and an npm package without the owner's scope installed with pnpm or a newer Yarn, is never in-house. When one repository uses the name without evidence, the name is public for every repository. A public package whose name one of your accounts also publishes says so in its tooltip: "Also published by acme/lib (not used here)."

A dependency without evidence is a public package: Pullwatch looks up its latest version in the public registry and its vulnerabilities in OSV.dev, as for any other package. When the account that publishes a package is removed or paused, or no longer lists the package, the next check treats it as public again.

Pullwatch reads your registries first, before it looks anything up, and leaves every in-house name out of every public registry: registry.npmjs.org and the others never see it. OSV.dev sees an in-house name only when an earlier check found that name in the public registry too, so a fork of a public package still gets the known vulnerabilities of that name; a name that only your registry knows never reaches OSV.dev. When reading your registry fails, Pullwatch keeps what the check before found.

When Pullwatch cannot read the latest version, the row says so instead of showing it as current:

- "Not checked: source Package registries of your accounts is off": the source is off under Settings, **Sources**. A package that was in-house before, with the same evidence, stays in-house and is not looked up publicly.
- "Not checked: no access to this account's package registry": the account may not read its registry. The tooltip says what to grant; see [What to grant](/using/packages/#what-to-grant).
- "Not checked: this account's package registry gave no latest version": the registry lists the package, but reading its versions failed, or it has none (for example a package without a linked repository). The latest version of the previous check stays when there was one. A name the public registry also knows is looked up there and checked by OSV.dev for this check; a name only your own registry knows is never sent anywhere.

Switching off a public registry, such as npm, does not affect an in-house package.

Which published package a dependency is compared with, by its ecosystem and its name (the evidence above then decides):

| Ecosystem | Matched on |
|---|---|
| npm | the name with its scope, exactly (`@acme/ui`). GitHub lists an npm package without its scope, so `ui` under `acme` is `@acme/ui`; a bare `ui` never matches a GitHub package, so a public package is never taken over |
| NuGet | the id, in any case |
| RubyGems, Packagist | the name, in any case |
| PyPI | the name, with `-`, `_`, `.` and case treated as equal |
| crates.io | the name, with `-` and `_` treated as equal |
| Go | the module path, exactly |

Not matched yet:

- Container images and Helm charts. Pullwatch reads a Dockerfile `FROM` line only as a runtime (Node, PHP, .NET), never as a dependency, so your own image on ghcr.io or a GitLab registry is not part of the dependency check. In Packages, their **Used by** shows "-".
- Maven. Pullwatch can match `groupId:artifactId` already, but it does not read Maven projects (`pom.xml`) for dependencies yet, so there is nothing to match.

## Per repository

The **Dependencies** tab of a repository page shows the same per workspace: the installed version, the newest version usable now, the latest version, and whether the package is direct, comes in through another package (with the shortest chain) or is for development only. In-house packages say **In-house** here too.

After the daily check, one notification lists the new versions of anything a repository is behind on. The first time a package is seen stays silent. Turn it off under Settings, Notifications, **New versions**.
