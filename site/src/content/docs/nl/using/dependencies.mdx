Eens per dag, en telkens als je **Alles checken** kiest, leest Pullwatch de manifesten en lockfiles op de standaardbranch van elke repository die je volgt. Het vindt de runtimes, frameworks en packages, en vergelijkt ze met wat actueel is. De dagelijkse check zet je uit onder Instellingen, Algemeen.

## Runtimes en frameworks

| Bestand | Wat Pullwatch vindt |
|---|---|
| `go.mod` | Go |
| `*.csproj`, `*.fsproj`, `Directory.Build.props` | .NET |
| `package.json` | Node (`engines`), Angular, React, Vue, Next.js, Nuxt |
| `composer.json` | PHP, Symfony, Laravel |
| `rust-toolchain`, `rust-toolchain.toml`, `Cargo.toml` in de root | Rust |
| `Package.swift` | Swift, vergeleken met de releases op swift.org |
| `.nvmrc`, `.node-version`, `pyproject.toml`, `.python-version` | Node, Python |
| `Dockerfile*` | basisimages zoals node, golang, python, dotnet, alpine, debian, ubuntu, nginx, postgres, redis, eclipse-temurin, rust, php en ruby |
| `.github/workflows/*.yml` | `python-version`, `node-version`, `go-version`, `dotnet-version` |

Versies worden vergeleken met [endoflife.date](https://endoflife.date) en krijgen een van vier standen: **Actueel**, **Achter** (er is een nieuwere major of minor; patches tellen niet), **EOL** of **Onbekend**. Swift heeft geen beleid voor het einde van de ondersteuning, dus Swift is nooit EOL.

Een paar regels houden de uitkomst eerlijk:

- Een eis die alleen een minimum is (`engines.node`, `php` in `composer.json`, `requires-python`, `rust-version`, versies in CI) valt weg als dezelfde taal ergens anders vastligt, zoals in een Docker-image, `.nvmrc` of `rust-toolchain`.
- Bij frameworks wint de geïnstalleerde versie uit `package-lock.json` of `composer.lock` van het minimum in het manifest.
- Een `go.mod` die als lokale kopie van een afhankelijkheid dient (`replace ... => ./path`), wordt genegeerd.
- Eigen Docker-images worden herkend aan een bekende naam voor het eerste streepje (`php-fpm-alpine:8.4` is PHP 8.4), en standaardwaarden van `ARG` in `FROM` worden ingevuld.

## Het onderdeel Afhankelijkheden

**Afhankelijkheden** in de zijbalk draait de check om: per runtime en package de nieuwste versie, en welke repositories nog op een oudere zitten. Het wordt bijgewerkt met de versiecheck (dagelijks, **Alles checken** en **Nu checken**), en de badge in de zijbalk telt de nieuwe versies die je nog niet hebt gezien en die je nu kunt nemen of die een kwetsbaarheid oplossen.

<Screenshot name="dependencies" alt="Het onderdeel Afhankelijkheden, verdeeld in Kan nu bijwerken, Manifest aanpassen nodig en Geblokkeerd, met lodash op één plek geblokkeerd door express en body-parser." />

- **Runtimes** (Go, Node, PHP, Python, .NET, Rust, Swift en Docker-images) worden vergeleken binnen hun releasecyclus, patches inbegrepen. Een repository op Go 1.27.3 ziet dat Go 1.27.4 beschikbaar is, en een op Go 1.26.9 ziet 1.26.10 zodra die uit is. Een nieuwere cyclus (Node 22 naar 25) staat in plaats daarvan bij de repository als achter. Een versie zonder patch (`go 1.27`, `node:22`) loopt nooit achter op patches.
- **Packages** zijn de directe afhankelijkheden, uit de root en elke workspace. Packages die alleen voor ontwikkeling zijn, worden zo gemarkeerd. Een package zonder exacte versie (een bereik zonder lockfile) telt niet mee. Frameworks (React, Angular, Vue, Next.js, Nuxt, Laravel, Symfony) staan er één keer, als package.
- De nieuwste versie komt uit het register van het package: proxy.golang.org, registry.npmjs.org, repo.packagist.org, api.nuget.org, pypi.org, crates.io en rubygems.org. Een package dat een van je gevolgde repositories zelf publiceert, komt in plaats daarvan uit je eigen register (zie [In-house packages](#in-house-packages)). Pre-releases tellen niet. Andere privémodules en Swift-packages komen onder **Niet te checken** terecht.

Zo weet Pullwatch dat een package direct is:

| Bestand | Directe packages |
|---|---|
| `go.mod` | regels zonder `// indirect` |
| `package-lock.json` (v2 en v3), `pnpm-lock.yaml` | de root en de workspaces |
| `packages.lock.json` | packages gemarkeerd als `Direct` |
| `Gemfile.lock` | de sectie `DEPENDENCIES` |
| `composer.lock`, `Cargo.lock`, `poetry.lock`, `uv.lock`, `yarn.lock` | de namen in `composer.json`, `Cargo.toml`, `pyproject.toml`, of de `package.json` van de root en elke workspace |
| .NET `PackageReference`, `requirements*.txt` | elk package, want die zijn al direct |

Packages voor alleen ontwikkeling komen uit `devDependencies`, `require-dev`, dev-groepen, en de blokken `group :development, :test` van een `Gemfile`.

De groepen zeggen wat een update vraagt: **Kan nu bijwerken** past binnen het bereik in je manifest, dus alleen de lockfile verandert; **Manifest aanpassen nodig** valt buiten dat bereik, zoals een nieuwe major-versie; **Geblokkeerd** betekent dat een ander package hem tegenhoudt, en de rij zegt welk.

Een package dat geen repo zelf vraagt en dat alleen via een ander package binnenkomt, staat onder **Alleen transitief, met een kwetsbaarheid** als het een bekende kwetsbaarheid heeft, met de keten die het binnenhaalt. Pullwatch zoekt de nieuwste versie alleen op voor packages die een repo zelf vraagt. Voor Rust komen de gevraagde bereiken uit elke `Cargo.toml` van een workspace, ook uit `[workspace.dependencies]` dat leden overnemen met `workspace = true`.

## In-house packages

Een dependency die een van je gevolgde repositories publiceert in het register van zijn eigen dienst (GitHub Packages, een register van GitLab of een feed van Azure Artifacts), en die je repository aantoonbaar daarvandaan haalt, is een in-house package. npmjs.com of nuget.org kennen een privé `@acme/ui` niet, dus Pullwatch haalt de nieuwste versie uit je eigen register, dat [Packages](/nl/using/packages/) op een rij zet. De rij zegt **In-house**, met een link naar de repository die het publiceert, en de tooltip zegt "Gepubliceerd door octocat/linguist: de nieuwste versie komt uit je eigen register." Bereiken, de updategroepen en wat een update tegenhoudt werken zoals bij elk ander package.

### Bewijs, niet de naam

Een naam alleen maakt een package niet van jou. Een organisatie kan een gepatchte fork van een openbaar package onder dezelfde naam publiceren, zoals `Newtonsoft.Json`, en een repository die het openbare package gebruikt, moet zijn openbare nieuwste versie en zijn bekende kwetsbaarheden houden. Daarom telt Pullwatch een dependency alleen als in-house met bewijs:

- npm: een naam met de scope van de eigenaar (`@acme/ui`, gepubliceerd door `acme`; bij GitLab de bovenste groep, bij Azure DevOps ook de organisatie).
- Go: het modulepad, dat zijn eigen host en eigenaar noemt.
- Elk ecosysteem: het register dat de lockfile of het manifest noemt, is het eigen register van het account voor dat ecosysteem. Pullwatch leest het uit `resolved` in `package-lock.json` en een klassieke `yarn.lock`, `remote:` in `Gemfile.lock`, `dist.url` in `composer.lock`, `--index-url` of `--extra-index-url` in een `requirements`-bestand, de bron van een package in `poetry.lock` en `uv.lock`, en `source` in `Cargo.lock`. Eigen registers zijn `npm.pkg.github.com`, `nuget.pkg.github.com` en `rubygems.pkg.github.com` met de eigenaar in het pad (bij GitHub Enterprise `npm.<host>` of `<host>/_registry/npm/`), `/api/v4/…/packages/…` op de GitLab-server van het account, en `pkgs.dev.azure.com/<organisatie>/…/_packaging/…` voor Azure Artifacts.

`packages.lock.json`, `pnpm-lock.yaml` en de `yarn.lock` van Yarn 2 en later noemen geen register per package, dus een NuGet-package, en een npm-package zonder de scope van de eigenaar dat met pnpm of een nieuwere Yarn is geïnstalleerd, is nooit in-house. Gebruikt één repository de naam zonder bewijs, dan is de naam openbaar voor elke repository. Een openbaar package waarvan een van je accounts de naam ook publiceert, zegt dat in de tooltip: "Ook gepubliceerd door acme/lib (hier niet gebruikt)."

Een dependency zonder bewijs is een openbaar package: Pullwatch zoekt de nieuwste versie op in het openbare register en de kwetsbaarheden in OSV.dev, zoals bij elk ander package. Is het account dat een package publiceert verwijderd of gepauzeerd, of noemt het het package niet meer, dan behandelt de volgende check het weer als openbaar.

Pullwatch leest eerst je registers, voordat het iets opzoekt, en laat elke in-house naam weg uit elk openbaar register: registry.npmjs.org en de andere zien hem nooit. OSV.dev ziet een in-house naam alleen als een eerdere check die naam ook in het openbare register vond, zodat een fork van een openbaar package toch de bekende kwetsbaarheden van die naam krijgt; een naam die alleen je eigen register kent, komt nooit bij OSV.dev. Lukt het lezen van je register niet, dan houdt Pullwatch wat de check ervoor vond.

Kan Pullwatch de nieuwste versie niet lezen, dan zegt de rij dat, in plaats van hem als actueel te tonen:

- "Niet gecontroleerd: bron Packageregisters van je accounts staat uit": de bron staat uit onder Instellingen, **Bronnen**. Een package dat eerder in-house was, blijft met hetzelfde bewijs in-house en wordt niet openbaar opgezocht.
- "Niet gecontroleerd: geen toegang tot het packageregister van dit account": het account mag zijn register niet lezen. De tooltip zegt wat je moet toestaan; zie [Wat je toestaat](/nl/using/packages/#wat-je-toestaat).
- "Niet gecontroleerd: het packageregister van dit account gaf geen nieuwste versie": het register noemt het package, maar het lezen van de versies mislukte, of het heeft er geen (bijvoorbeeld een package zonder gekoppelde repository). De nieuwste versie van de vorige check blijft als die er was. Een naam die het publieke register ook kent, zoekt de check deze keer daar op en laat hij door OSV.dev controleren; een naam die alleen je eigen register kent, gaat nergens heen.

Een openbaar register uitzetten, zoals npm, raakt een in-house package niet.

Met welk gepubliceerd package een dependency vergeleken wordt, op zijn ecosysteem en zijn naam (daarna beslist het bewijs hierboven):

| Ecosysteem | Gematcht op |
|---|---|
| npm | de naam met zijn scope, precies (`@acme/ui`). GitHub noemt een npm-package zonder scope, dus `ui` onder `acme` is `@acme/ui`; een kale `ui` matcht nooit een GitHub-package, zodat een openbaar package nooit wordt overgenomen |
| NuGet | de id, hoofdletters maken niet uit |
| RubyGems, Packagist | de naam, hoofdletters maken niet uit |
| PyPI | de naam, met `-`, `_`, `.` en hoofdletters als gelijk |
| crates.io | de naam, met `-` en `_` als gelijk |
| Go | het modulepad, precies |

Nog niet gematcht:

- Container-images en Helm-charts. Pullwatch leest een regel `FROM` in een Dockerfile alleen als runtime (Node, PHP, .NET), nooit als dependency, dus je eigen image op ghcr.io of in een register van GitLab hoort niet bij de dependency-check. In Packages staat bij **Gebruikt door** dan "-".
- Maven. Pullwatch kan `groupId:artifactId` al matchen, maar leest Maven-projecten (`pom.xml`) nog niet op dependencies, dus er is niets om te matchen.

## Per repository

Het tabblad **Afhankelijkheden** van de pagina van een repository toont hetzelfde per workspace: de geïnstalleerde versie, de nieuwste versie die nu kan, de allernieuwste versie, en of het package direct is, via een ander package binnenkomt (met de kortste keten) of alleen voor ontwikkeling is. In-house packages zeggen ook hier **In-house**.

<Screenshot name="repo-packages" alt="Het tabblad Afhankelijkheden van hello-world: lodash in twee versies, express geblokkeerd, het in-house package @octocat/greeting van 1.2.0 naar 1.4.0, vite en jest met Alleen dev, body-parser en qs via express." />

Na de dagelijkse check zet één melding de nieuwe versies op een rij van alles waarop een repository achterloopt. De eerste keer dat een package gezien wordt, blijft het stil. Zet het uit onder Instellingen, Meldingen, **Nieuwe versies**.
