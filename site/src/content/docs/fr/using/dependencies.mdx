Une fois par jour, et chaque fois que vous choisissez **Tout vérifier**, Pullwatch lit les manifestes et les fichiers de verrouillage sur la branche par défaut de chaque dépôt que vous suivez. Il y trouve les runtimes, les frameworks et les paquets, et les compare à ce qui est à jour. Vous pouvez désactiver la vérification quotidienne dans Réglages, Général.

## Runtimes et frameworks

| Fichier | Ce que Pullwatch trouve |
|---|---|
| `go.mod` | Go |
| `*.csproj`, `*.fsproj`, `Directory.Build.props` | .NET |
| `package.json` | Node (`engines`), Angular, React, Vue, Next.js, Nuxt |
| `composer.json` | PHP, Symfony, Laravel |
| `rust-toolchain`, `rust-toolchain.toml`, `Cargo.toml` à la racine | Rust |
| `Package.swift` | Swift, comparé aux versions publiées sur swift.org |
| `.nvmrc`, `.node-version`, `pyproject.toml`, `.python-version` | Node, Python |
| `Dockerfile*` | les images de base comme node, golang, python, dotnet, alpine, debian, ubuntu, nginx, postgres, redis, eclipse-temurin, rust, php et ruby |
| `.github/workflows/*.yml` | `python-version`, `node-version`, `go-version`, `dotnet-version` |

Les versions sont comparées à [endoflife.date](https://endoflife.date) et reçoivent l’un de quatre états : **À jour**, **En retard** (une version majeure ou mineure plus récente existe ; les correctifs ne comptent pas), **EOL** ou **Inconnu**. Swift n’a pas de politique de fin de vie, il n’est donc jamais EOL.

Quelques règles gardent le résultat fiable :

- Une exigence qui n’est qu’un minimum (`engines.node`, `php` dans `composer.json`, `requires-python`, `rust-version`, les versions en CI) est ignorée quand le même langage est fixé ailleurs, comme une image Docker, `.nvmrc` ou `rust-toolchain`.
- Pour les frameworks, la version installée de `package-lock.json` ou `composer.lock` l’emporte sur le minimum du manifeste.
- Un `go.mod` utilisé comme copie locale d’une dépendance (`replace ... => ./path`) est ignoré.
- Les images Docker personnalisées sont reconnues par un nom connu avant le premier tiret (`php-fpm-alpine:8.4` est PHP 8.4), et les valeurs par défaut des `ARG` dans `FROM` sont remplies.

## La section Dépendances

**Dépendances** dans la barre latérale présente la vérification dans l’autre sens : pour chaque runtime et chaque paquet, la dernière version, et les dépôts qui sont encore sur une version plus ancienne. Elle se met à jour avec la vérification des versions (quotidienne, **Tout vérifier** et **Vérifier maintenant**), et son badge dans la barre latérale compte les nouvelles versions que vous n’avez pas encore vues et que vous pouvez prendre maintenant ou qui corrigent une vulnérabilité.

<Screenshot name="dependencies" alt="La section Dépendances regroupée en Mise à jour possible, Manifeste à modifier et Bloqué, avec lodash bloqué à un endroit par express et body-parser." />

- **Les runtimes** (Go, Node, PHP, Python, .NET, Rust, Swift et les images Docker) sont comparés au sein de leur cycle de publication, correctifs compris. Un dépôt sur Go 1.27.3 voit que Go 1.27.4 est disponible, et un dépôt sur Go 1.26.9 voit 1.26.10 dès sa sortie. Un cycle plus récent (de Node 22 à 25) apparaît plutôt sur le dépôt comme en retard. Une version sans correctif (`go 1.27`, `node:22`) n’est jamais en retard sur les correctifs.
- **Les paquets** sont les dépendances directes, de la racine et de chaque espace de travail. Les paquets réservés au développement sont signalés comme tels. Un paquet sans version exacte (une plage sans fichier de verrouillage) n’est pas compté. Les frameworks (React, Angular, Vue, Next.js, Nuxt, Laravel, Symfony) apparaissent une seule fois, comme paquet.
- La dernière version vient du registre du paquet : proxy.golang.org, registry.npmjs.org, repo.packagist.org, api.nuget.org, pypi.org, crates.io et rubygems.org. Un paquet qu’un de vos dépôts suivis publie lui-même vient plutôt de votre propre registre (voir [Paquets internes](#paquets-internes)). Les préversions ne comptent pas. Les autres modules privés et les paquets Swift se retrouvent sous **Impossible à vérifier**.

Comment Pullwatch sait qu’un paquet est direct :

| Fichier | Paquets directs |
|---|---|
| `go.mod` | les lignes sans `// indirect` |
| `package-lock.json` (v2 et v3), `pnpm-lock.yaml` | la racine et les espaces de travail |
| `packages.lock.json` | les paquets marqués `Direct` |
| `Gemfile.lock` | la section `DEPENDENCIES` |
| `composer.lock`, `Cargo.lock`, `poetry.lock`, `uv.lock`, `yarn.lock` | les noms de `composer.json`, `Cargo.toml`, `pyproject.toml`, ou du `package.json` de la racine et de chaque espace de travail |
| .NET `PackageReference`, `requirements*.txt` | chaque paquet, puisqu’ils sont déjà directs |

Les paquets réservés au développement viennent de `devDependencies`, `require-dev`, des groupes dev, et des blocs `group :development, :test` d’un `Gemfile`.

Les groupes vous disent ce qu’une mise à jour demande : **Mise à jour possible** reste dans la plage de votre manifeste, donc seul le fichier de verrouillage change ; **Manifeste à modifier** sort de cette plage, comme une nouvelle version majeure ; **Bloqué** signifie qu’un autre paquet la retient, et la ligne indique lequel.

Un paquet qu’aucun dépôt ne demande lui-même, et qui n’arrive que par un autre paquet, apparaît sous **Seulement transitif, avec une vulnérabilité** quand il a une vulnérabilité connue, avec la chaîne qui l’amène. Pullwatch ne cherche la dernière version que pour les paquets qu’un dépôt demande lui-même. Pour Rust, les plages demandées viennent de chaque `Cargo.toml` d’un workspace, y compris des `[workspace.dependencies]` que les membres reprennent avec `workspace = true`.

## Paquets internes

Une dépendance qu’un de vos dépôts suivis publie dans le registre de son propre service (GitHub Packages, un registre GitLab ou un flux Azure Artifacts), et que votre dépôt obtient de façon prouvée à cet endroit, est un paquet interne. npmjs.com ou nuget.org ne connaissent pas un `@acme/ui` privé, donc Pullwatch prend sa dernière version dans votre registre, que [Paquets](/fr/using/packages/) liste. La ligne indique **Interne**, avec un lien vers le dépôt qui le publie, et son infobulle dit « Publié par octocat/linguist : la dernière version provient de votre propre registre. ». Les plages, les groupes de mise à jour et ce qui bloque une mise à jour fonctionnent comme pour tout autre paquet.

### Une preuve, pas le nom

Un nom seul ne fait pas d’un paquet le vôtre. Une organisation peut publier un fork corrigé d’un paquet public sous le même nom, comme `Newtonsoft.Json`, et un dépôt qui utilise le paquet public doit garder sa dernière version publique et ses vulnérabilités connues. Pullwatch ne compte donc une dépendance comme interne qu’avec une preuve :

- npm : un nom avec le scope du propriétaire (`@acme/ui` publié par `acme` ; sur GitLab le groupe de premier niveau, sur Azure DevOps aussi l’organisation).
- Go : le chemin du module, qui nomme son propre hôte et son propriétaire.
- Tout écosystème : le registre que nomme le lockfile ou le manifeste est le propre registre du compte pour cet écosystème. Pullwatch le lit dans `resolved` de `package-lock.json` et d’un `yarn.lock` classique, `remote:` de `Gemfile.lock`, `dist.url` de `composer.lock`, `--index-url` ou `--extra-index-url` d’un fichier `requirements`, la source d’un paquet dans `poetry.lock` et `uv.lock`, et `source` de `Cargo.lock`. Les registres propres sont `npm.pkg.github.com`, `nuget.pkg.github.com` et `rubygems.pkg.github.com` avec le propriétaire dans le chemin (sur GitHub Enterprise `npm.<hôte>` ou `<hôte>/_registry/npm/`), `/api/v4/…/packages/…` sur le serveur GitLab du compte, et `pkgs.dev.azure.com/<organisation>/…/_packaging/…` pour Azure Artifacts.

`packages.lock.json`, `pnpm-lock.yaml` et le `yarn.lock` de Yarn 2 et suivants ne nomment aucun registre par paquet : un paquet NuGet, et un paquet npm sans le scope du propriétaire installé avec pnpm ou un Yarn récent, n’est donc jamais interne. Quand un dépôt utilise le nom sans preuve, le nom est public pour tous les dépôts. Un paquet public dont un de vos comptes publie aussi le nom le dit dans son infobulle : « Également publié par acme/lib (non utilisé ici) ».

Une dépendance sans preuve est un paquet public : Pullwatch cherche sa dernière version dans le registre public et ses vulnérabilités dans OSV.dev, comme pour tout autre paquet. Quand le compte qui publie un paquet est supprimé ou mis en pause, ou ne liste plus le paquet, la vérification suivante le traite de nouveau comme public.

Pullwatch lit d’abord vos registres, avant toute recherche, et laisse chaque nom interne en dehors de tous les registres publics : registry.npmjs.org et les autres ne le voient jamais. OSV.dev ne voit un nom interne que si une vérification précédente a aussi trouvé ce nom dans le registre public, pour qu’un fork d’un paquet public reçoive quand même les vulnérabilités connues de ce nom ; un nom que seul votre registre connaît n’atteint jamais OSV.dev. Quand la lecture de votre registre échoue, Pullwatch garde ce que la vérification précédente a trouvé.

Quand Pullwatch ne peut pas lire la dernière version, la ligne le dit au lieu de l’afficher comme à jour :

- « Non vérifié : la source Registres de paquets de vos comptes est désactivée » : la source est désactivée dans Réglages, **Sources**. Un paquet qui était interne le reste avec la même preuve et n’est pas recherché publiquement.
- « Non vérifié : aucun accès au registre de paquets de ce compte » : le compte ne peut pas lire son registre. L’infobulle dit ce qu’il faut accorder ; voir [Les autorisations à accorder](/fr/using/packages/#les-autorisations-à-accorder).
- « Non vérifié : le registre de paquets de ce compte n'a donné aucune dernière version » : le registre nomme le paquet, mais la lecture de ses versions a échoué, ou il n’en a aucune (par exemple un paquet sans dépôt lié). La dernière version de la vérification précédente reste, s’il y en avait une. Un nom que le registre public connaît aussi y est recherché pour cette vérification et contrôlé par OSV.dev ; un nom que seul votre propre registre connaît n’est envoyé nulle part.

Désactiver un registre public, comme npm, n’a aucun effet sur un paquet interne.

Le paquet publié auquel une dépendance est comparée, selon son écosystème et son nom (la preuve ci-dessus décide ensuite) :

| Écosystème | Associé sur |
|---|---|
| npm | le nom avec son scope, exactement (`@acme/ui`). GitHub liste un paquet npm sans son scope, donc `ui` sous `acme` est `@acme/ui` ; un `ui` seul n’est jamais associé à un paquet GitHub, donc un paquet public n’est jamais repris |
| NuGet | l’identifiant, sans tenir compte de la casse |
| RubyGems, Packagist | le nom, sans tenir compte de la casse |
| PyPI | le nom, `-`, `_`, `.` et la casse étant considérés comme égaux |
| crates.io | le nom, `-` et `_` étant considérés comme égaux |
| Go | le chemin du module, exactement |

Pas encore associés :

- Les images de conteneur et les charts Helm. Pullwatch lit une ligne `FROM` d’un Dockerfile seulement comme un runtime (Node, PHP, .NET), jamais comme une dépendance, donc votre propre image sur ghcr.io ou dans un registre GitLab ne fait pas partie de la vérification des dépendances. Dans Paquets, leur colonne **Utilisé par** affiche « - ».
- Maven. Pullwatch sait déjà associer `groupId:artifactId`, mais il ne lit pas encore les dépendances des projets Maven (`pom.xml`), il n’y a donc rien à associer.

## Par dépôt

L’onglet **Dépendances** d’une page de dépôt affiche la même chose par espace de travail : la version installée, la version la plus récente utilisable maintenant, la dernière version, et si le paquet est direct, s’il arrive par un autre paquet (avec la chaîne la plus courte) ou s’il est réservé au développement. Les paquets internes indiquent aussi **Interne** ici.

<Screenshot name="repo-packages" alt="L’onglet Dépendances de hello-world : lodash en deux versions, express bloqué, le paquet interne @octocat/greeting de 1.2.0 à 1.4.0, vite et jest en dev uniquement, body-parser et qs via express." />

Après la vérification quotidienne, une notification liste les nouvelles versions de tout ce sur quoi un dépôt est en retard. La première fois qu’un paquet est vu, rien n’est notifié. Désactivez-la dans Réglages, Notifications, **Nouvelles versions**.
