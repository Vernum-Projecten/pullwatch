Einmal am Tag, und immer wenn du **Alle prüfen** wählst, liest Pullwatch die Manifeste und Lockfiles auf dem Standard-Branch jedes Repositorys, dem du folgst. Es findet die Runtimes, Frameworks und Pakete und vergleicht sie mit dem aktuellen Stand. Die tägliche Prüfung kannst du unter Einstellungen, Allgemein ausschalten.

## Runtimes und Frameworks

| Datei | Was Pullwatch findet |
|---|---|
| `go.mod` | Go |
| `*.csproj`, `*.fsproj`, `Directory.Build.props` | .NET |
| `package.json` | Node (`engines`), Angular, React, Vue, Next.js, Nuxt |
| `composer.json` | PHP, Symfony, Laravel |
| `rust-toolchain`, `rust-toolchain.toml`, `Cargo.toml` im Root | Rust |
| `Package.swift` | Swift, verglichen mit den Releases auf swift.org |
| `.nvmrc`, `.node-version`, `pyproject.toml`, `.python-version` | Node, Python |
| `Dockerfile*` | Basis-Images wie node, golang, python, dotnet, alpine, debian, ubuntu, nginx, postgres, redis, eclipse-temurin, rust, php und ruby |
| `.github/workflows/*.yml` | `python-version`, `node-version`, `go-version`, `dotnet-version` |

Versionen werden mit [endoflife.date](https://endoflife.date) verglichen und bekommen einen von vier Zuständen: **Aktuell**, **Veraltet** (es gibt eine neuere Major- oder Minor-Version; Patches zählen nicht), **EOL** oder **Unbekannt**. Swift hat keine Regel für das Support-Ende und ist deshalb nie EOL.

Ein paar Regeln halten das Ergebnis ehrlich:

- Eine Anforderung, die nur ein Minimum ist (`engines.node`, `php` in `composer.json`, `requires-python`, `rust-version`, Versionen in CI), fällt weg, wenn dieselbe Sprache anderswo fest angegeben ist, etwa in einem Docker-Image, `.nvmrc` oder `rust-toolchain`.
- Bei Frameworks hat die installierte Version aus `package-lock.json` oder `composer.lock` Vorrang vor dem Minimum im Manifest.
- Ein `go.mod`, das als lokale Kopie einer Abhängigkeit dient (`replace ... => ./path`), wird ignoriert.
- Eigene Docker-Images werden an einem bekannten Namen vor dem ersten Bindestrich erkannt (`php-fpm-alpine:8.4` ist PHP 8.4), und Standardwerte von `ARG` in `FROM` werden eingesetzt.

## Der Bereich Abhängigkeiten

**Abhängigkeiten** in der Seitenleiste dreht die Prüfung um: pro Runtime und Paket die neueste Version und welche Repositories noch auf einer älteren sind. Der Bereich wird mit der Versionsprüfung aktualisiert (täglich, **Alle prüfen** und **Jetzt prüfen**), und sein Badge in der Seitenleiste zählt die neuen Versionen, die du noch nicht gesehen hast und die du jetzt übernehmen kannst oder die eine Schwachstelle beheben.

<Screenshot name="dependencies" alt="Der Bereich Abhängigkeiten, gruppiert nach Jetzt aktualisierbar, Manifest muss geändert werden und Blockiert, mit lodash, das an einer Stelle von express und body-parser blockiert wird." />

- **Runtimes** (Go, Node, PHP, Python, .NET, Rust, Swift und Docker-Images) werden innerhalb ihres Releasezyklus verglichen, Patches eingeschlossen. Ein Repository auf Go 1.27.3 sieht, dass Go 1.27.4 verfügbar ist, und eines auf Go 1.26.9 sieht 1.26.10, sobald es erscheint. Ein neuerer Zyklus (Node 22 auf 25) erscheint stattdessen beim Repository als veraltet. Eine Version ohne Patch (`go 1.27`, `node:22`) ist bei Patches nie veraltet.
- **Pakete** sind die direkten Abhängigkeiten, aus dem Root und jedem Workspace. Pakete nur für die Entwicklung sind als solche markiert. Ein Paket ohne exakte Version (ein Bereich ohne Lockfile) wird nicht gezählt. Frameworks (React, Angular, Vue, Next.js, Nuxt, Laravel, Symfony) erscheinen einmal, als Paket.
- Die neueste Version kommt aus der Registry des Pakets: proxy.golang.org, registry.npmjs.org, repo.packagist.org, api.nuget.org, pypi.org, crates.io und rubygems.org. Ein Paket, das eines der Repositories, denen du folgst, selbst veröffentlicht, kommt stattdessen aus deiner eigenen Registry (siehe [Hauseigene Pakete](#hauseigene-pakete)). Vorab-Releases zählen nicht. Andere private Module und Swift-Pakete landen unter **Nicht prüfbar**.

Woran Pullwatch erkennt, dass ein Paket direkt ist:

| Datei | Direkte Pakete |
|---|---|
| `go.mod` | Zeilen ohne `// indirect` |
| `package-lock.json` (v2 und v3), `pnpm-lock.yaml` | der Root und die Workspaces |
| `packages.lock.json` | Pakete, die als `Direct` markiert sind |
| `Gemfile.lock` | der Abschnitt `DEPENDENCIES` |
| `composer.lock`, `Cargo.lock`, `poetry.lock`, `uv.lock`, `yarn.lock` | die Namen in `composer.json`, `Cargo.toml`, `pyproject.toml` oder der `package.json` des Roots und jedes Workspace |
| .NET `PackageReference`, `requirements*.txt` | jedes Paket, da sie ohnehin direkt sind |

Pakete nur für die Entwicklung kommen aus `devDependencies`, `require-dev`, Dev-Gruppen und den Blöcken `group :development, :test` eines `Gemfile`.

Die Gruppen sagen dir, was ein Update braucht: **Jetzt aktualisierbar** passt in den Bereich in deinem Manifest, also ändert sich nur die Lockfile; **Manifest muss geändert werden** liegt außerhalb dieses Bereichs, etwa eine neue Major-Version; **Blockiert** heißt, dass ein anderes Paket es zurückhält, und die Zeile sagt, welches.

Ein Paket, das kein Repository selbst verlangt und das nur über ein anderes Paket hereinkommt, steht unter **Nur transitiv, mit einer Schwachstelle**, wenn es eine bekannte Schwachstelle hat, mit der Kette, die es hereinholt. Pullwatch sucht die neueste Version nur für Pakete, die ein Repository selbst verlangt. Für Rust kommen die verlangten Bereiche aus jeder `Cargo.toml` eines Workspace, auch aus `[workspace.dependencies]`, das Mitglieder mit `workspace = true` übernehmen.

## Hauseigene Pakete

Eine Abhängigkeit, die eines der Repositories, denen du folgst, in der Registry seines eigenen Dienstes veröffentlicht (GitHub Packages, eine Registry von GitLab oder ein Feed von Azure Artifacts), und die dein Repository nachweislich von dort bezieht, ist ein hauseigenes Paket. npmjs.com oder nuget.org kennen ein privates `@acme/ui` nicht, deshalb nimmt Pullwatch seine neueste Version aus deiner Registry, die [Pakete](/de/using/packages/) auflistet. Die Zeile sagt **Hauseigen**, mit einem Link zum Repository, das es veröffentlicht, und ihr Tooltip sagt „Veröffentlicht von octocat/linguist: Die neueste Version kommt aus deiner eigenen Registry.“ Bereiche, die Update-Gruppen und was ein Update aufhält funktionieren wie bei jedem anderen Paket.

### Nachweis statt Name

Ein Name allein macht ein Paket nicht zu deinem. Eine Organisation kann einen gepatchten Fork eines öffentlichen Pakets unter demselben Namen veröffentlichen, etwa `Newtonsoft.Json`, und ein Repository, das das öffentliche Paket verwendet, muss dessen öffentliche neueste Version und dessen bekannte Schwachstellen behalten. Deshalb zählt Pullwatch eine Abhängigkeit nur mit Nachweis als hauseigen:

- npm: ein Name mit dem Scope des Owners (`@acme/ui`, veröffentlicht von `acme`; bei GitLab die oberste Gruppe, bei Azure DevOps auch die Organisation).
- Go: der Modulpfad, der seinen eigenen Host und Owner nennt.
- Jedes Ökosystem: Die Registry, die die Lockfile oder das Manifest nennt, ist die eigene Registry des Kontos für dieses Ökosystem. Pullwatch liest sie aus `resolved` in `package-lock.json` und einer klassischen `yarn.lock`, `remote:` in `Gemfile.lock`, `dist.url` in `composer.lock`, `--index-url` oder `--extra-index-url` in einer `requirements`-Datei, der Quelle eines Pakets in `poetry.lock` und `uv.lock` und `source` in `Cargo.lock`. Eigene Registries sind `npm.pkg.github.com`, `nuget.pkg.github.com` und `rubygems.pkg.github.com` mit dem Owner im Pfad (bei GitHub Enterprise `npm.<host>` oder `<host>/_registry/npm/`), `/api/v4/…/packages/…` auf dem GitLab-Server des Kontos und `pkgs.dev.azure.com/<organisation>/…/_packaging/…` für Azure Artifacts.

`packages.lock.json`, `pnpm-lock.yaml` und die `yarn.lock` von Yarn 2 und neuer nennen keine Registry pro Paket, also ist ein NuGet-Paket, und ein npm-Paket ohne den Scope des Owners, das mit pnpm oder einem neueren Yarn installiert wurde, nie hauseigen. Verwendet ein Repository den Namen ohne Nachweis, ist der Name für jedes Repository öffentlich. Ein öffentliches Paket, dessen Namen eines deiner Konten ebenfalls veröffentlicht, sagt das im Tooltip: „Auch veröffentlicht von acme/lib (hier nicht verwendet)“.

Eine Abhängigkeit ohne Nachweis ist ein öffentliches Paket: Pullwatch schlägt ihre neueste Version in der öffentlichen Registry und ihre Schwachstellen bei OSV.dev nach, wie bei jedem anderen Paket. Wird das Konto, das ein Paket veröffentlicht, entfernt oder pausiert, oder nennt es das Paket nicht mehr, behandelt die nächste Prüfung es wieder als öffentlich.

Pullwatch liest zuerst deine Registries, bevor es irgendetwas nachschlägt, und lässt jeden hauseigenen Namen aus jeder öffentlichen Registry heraus: registry.npmjs.org und die anderen sehen ihn nie. OSV.dev sieht einen hauseigenen Namen nur, wenn eine frühere Prüfung diesen Namen auch in der öffentlichen Registry gefunden hat, damit ein Fork eines öffentlichen Pakets trotzdem die bekannten Schwachstellen dieses Namens bekommt; ein Name, den nur deine Registry kennt, erreicht OSV.dev nie. Schlägt das Lesen deiner Registry fehl, behält Pullwatch, was die vorige Prüfung gefunden hat.

Kann Pullwatch die neueste Version nicht lesen, sagt die Zeile das, statt sie als aktuell zu zeigen:

- „Nicht geprüft: Quelle Paket-Registrys deiner Konten ist aus“: Die Quelle ist unter Einstellungen, **Quellen** ausgeschaltet. Ein Paket, das vorher hauseigen war, bleibt mit demselben Nachweis hauseigen und wird nicht öffentlich nachgeschlagen.
- „Nicht geprüft: kein Zugriff auf die Paket-Registry dieses Kontos“: Das Konto darf seine Registry nicht lesen. Der Tooltip sagt, was du freigeben musst; siehe [Welche Berechtigung nötig ist](/de/using/packages/#welche-berechtigung-nötig-ist).
- „Nicht geprüft: die Paket-Registry dieses Kontos lieferte keine neueste Version“: Die Registry nennt das Paket, aber das Lesen seiner Versionen schlug fehl, oder es hat keine (zum Beispiel ein Paket ohne verknüpftes Repository). Die neueste Version der vorigen Prüfung bleibt, wenn es eine gab. Einen Namen, den auch die öffentliche Registry kennt, schlägt die Prüfung diesmal dort nach und lässt ihn von OSV.dev prüfen; ein Name, den nur deine eigene Registry kennt, geht nirgendwohin.

Schaltest du eine öffentliche Registry aus, etwa npm, betrifft das kein hauseigenes Paket.

Mit welchem veröffentlichten Paket eine Abhängigkeit verglichen wird, nach ihrem Ökosystem und ihrem Namen (danach entscheidet der Nachweis oben):

| Ökosystem | Abgeglichen über |
|---|---|
| npm | den Namen mit seinem Scope, exakt (`@acme/ui`). GitHub listet ein npm-Paket ohne seinen Scope, also ist `ui` unter `acme` gleich `@acme/ui`; ein bloßes `ui` passt nie zu einem Paket auf GitHub, sodass ein öffentliches Paket nie übernommen wird |
| NuGet | die ID, in beliebiger Schreibweise |
| RubyGems, Packagist | den Namen, in beliebiger Schreibweise |
| PyPI | den Namen, wobei `-`, `_`, `.` und Groß- und Kleinschreibung als gleich gelten |
| crates.io | den Namen, wobei `-` und `_` als gleich gelten |
| Go | den Modulpfad, exakt |

Noch nicht abgeglichen:

- Container-Images und Helm-Charts. Pullwatch liest eine `FROM`-Zeile in einem Dockerfile nur als Runtime (Node, PHP, .NET), nie als Abhängigkeit, also gehört dein eigenes Image auf ghcr.io oder in einer Registry von GitLab nicht zur Prüfung der Abhängigkeiten. In Pakete zeigt ihr **Verwendet von** „-“.
- Maven. Pullwatch kann `groupId:artifactId` schon abgleichen, liest aber Maven-Projekte (`pom.xml`) noch nicht nach Abhängigkeiten, es gibt also nichts abzugleichen.

## Pro Repository

Der Tab **Abhängigkeiten** auf der Seite eines Repositorys zeigt dasselbe pro Workspace: die installierte Version, die neueste Version, die jetzt nutzbar ist, die allerneueste Version und ob das Paket direkt ist, über ein anderes Paket kommt (mit der kürzesten Kette) oder nur für die Entwicklung ist. Hauseigene Pakete zeigen auch hier **Hauseigen**.

<Screenshot name="repo-packages" alt="Der Tab Abhängigkeiten von hello-world: lodash in zwei Versionen, express blockiert, das hauseigene Paket @octocat/greeting von 1.2.0 auf 1.4.0, vite und jest nur für die Entwicklung, body-parser und qs über express." />

Nach der täglichen Prüfung listet eine Mitteilung die neuen Versionen von allem, wobei ein Repository veraltet ist. Wird ein Paket zum ersten Mal gesehen, bleibt das still. Schalte es unter Einstellungen, Mitteilungen, **Neue Versionen** aus.
